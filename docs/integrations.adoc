= Integrations: SmugMug, WordPress and Meshy
:toc:

Credentials are stored in the macOS Keychain (services `gitwebsite-smugmug`,
`gitwebsite-wordpress` and `gitwebsite-meshy`). The `auth` commands are interactive — run them yourself in a
terminal; secrets are never echoed or logged.

== SmugMug: hosting images and video

SmugMug serves large photos and video from its CDN; the site refers to them through the media
library as `media:<key>`.

=== One-time setup

. Get an API key and secret at https://api.smugmug.com/api/developer/apply.
. Run `gw smugmug auth`: paste the key and secret, open the printed authorisation URL, approve
  access, and paste back the six-digit code.
. Check with `gw smugmug whoami`.

=== Using it

[source,console]
----
gw smugmug albums                                         # name, AlbumKey, address
gw smugmug upload bench.jpg --album AbC123 --key bench-front --alt "The finished bench"
gw smugmug import https://photos.smugmug.com/.../i-Xyz789 --key sled-overview
gw smugmug sync-album AbC123 --prefix workbench           # workbench-1, workbench-2, ...
----

Each command records the item in `site/media.yaml` (CDN URL, thumbnail, image and album
keys) and prints the snippet to paste:

[source,asciidoc]
----
image::media:bench-front[The finished bench]
video::media:sled-demo[width=100%]
----

== WordPress: import, then cross-post

=== Importing existing posts

Public posts can be imported without credentials. Each becomes a *draft* article, converted
from HTML to AsciiDoc with pandoc, with a registry entry recording where it came from:

[source,console]
----
gw wordpress import --from example.wordpress.com --dry-run      # see what would happen
gw wordpress import --from example.wordpress.com                # import as drafts
gw wordpress import --wxr export.xml                            # from a WordPress export file
----

Options: `--since YYYY-MM-DD`, `--status draft|published`, `--limit N`, `--download-images`
(copy images into each post's bundle instead of linking to WordPress). Re-running skips posts
already imported. Imported posts get `:source: wordpress-<host>-<id>`; areas are filled in
where a WordPress category matches an area, and marked `// TODO areas` otherwise — review and
`gw release` the ones to keep.

=== Cross-posting new posts

[source,console]
----
gw wordpress auth --host example.wordpress.com
gw wordpress crosspost articles/router-sled                     # creates a WordPress draft
gw wordpress crosspost articles/router-sled --status publish
----

The WordPress copy ends with "Originally published at …" linking back to this site, and the
remote post is recorded in the registry. Only locally published items can be cross-posted.

== Meshy models

https://www.meshy.ai[Meshy] makes 3D models; it keeps each model's download links for about three
days, after which getting the files back costs a paid remesh (5 credits). gitwebsite keeps a local
git repository of your Meshy models in step with your account, so nothing expires unseen.

The work is done by the models repository's own sync tool, `<repo>/tools/sync`: it lists your Meshy
tasks, downloads new models while the links are live (free), lays out build plates, renders images,
regenerates the catalogue and commits. gitwebsite runs it, records the result, and shows the models.
Each model folder holds a print-ready `<slug>-print.stl` (one part) or `<slug>-plate*.stl` (build
plates) in Git LFS, `images/`, `README.md` and `meshy.json`; the full-resolution `<slug>.stl` and
Meshy's `.glb`, `.3mf`, `.usdz` and `.blend` files are kept beside them locally and are not in git.

=== Setting up

. Store the API key (from https://www.meshy.ai/settings/api) in the Keychain — `security` prompts
  for it, so it never appears in your shell history:
+
[source,sh]
----
security add-generic-password -s gitwebsite-meshy -a api-key -w
----
. Point gitwebsite at the models repository (by default it uses `~/code/claude_world/meshy-models`
  or `~/code/meshy-models` if one exists):
+
[source,sh]
----
gw meshy config --repo ~/code/meshy-models     # --interval 24 (hours), --enable / --disable
----

The settings go in the user config (`~/.config/gitwebsite/config.toml`):

[source,toml]
----
[meshy]
repo = "/Users/me/code/meshy-models"
interval_hours = 24
enabled = true
----

=== Commands

[source,sh]
----
gw meshy status                          # last sync, next one, credit balance, models, new, expired
gw meshy sync                            # now: free downloads only (streams the tool's output)
gw meshy sync --dry-run                  # look only: what is waiting on Meshy, what recovery would cost
gw meshy sync --recover --max-credits 25 # ALSO recover expired models: spends up to 25 credits
gw meshy models [--project amiga]        # the models: folder, triangles, print size, parts, name
----

`--recover` is never implied: it needs `--max-credits`, and the sync tool also stops before the
balance would fall below 250 credits. It never pays twice for the same model.

=== The schedule

While `gw serve` or the desktop app runs, it syncs every `interval_hours` (default 24) — *without*
`--recover`, so a scheduled sync only ever downloads free. The first check is about a minute and a
half after start: if the last sync is older than the interval (or there has never been one), it runs
then. A manual sync counts, so syncing by hand pushes the next scheduled one back; a failed sync is
retried after an hour. Dry runs don't count.

* Runs never overlap, whoever starts them (app, CLI, MCP): a lock file holds the running process.
* Each run's output is kept in `~/.config/gitwebsite/meshy/logs/`, and the last 20 results in
  `meshy/history.json`.
* When new models arrive you get a macOS notification, and the app shows them (a count beside
  *Models*, and a banner on the page until you dismiss it).
* Models whose links expired before a sync got them are listed — with what recovering them would
  cost — but never recovered automatically.

=== In the app

*Models* shows the last and next sync, the credit balance, a *Sync now* button (with the tool's
output live while it runs), *Check Meshy* (a dry run), filter chips per project, and a card per
model. A card opens the model: every view, its size, triangles and parts, the print files, *Show in
Finder*, and its README. If any models have expired, *Recover N models (N×5 credits)* asks you to
confirm the exact number of credits first.

The REST API: `GET /api/meshy/status`, `POST /api/meshy/sync` (`{"recover": false}` or
`{"recover": true, "max_credits": N}`, `"dry_run": true`; 409 while one runs), `GET /api/meshy/models`
(`?project=`), `GET /api/meshy/models/{project}/{slug}` (with the README), `GET /api/meshy/file?path=`
(images from the models repository only), `GET /api/meshy/log` (`?run=&offset=`), `GET|PUT
/api/meshy/config`, `POST /api/meshy/reveal`, `POST /api/meshy/seen`. MCP tools: `meshy_status`,
`meshy_sync` (recover needs an explicit `max_credits`), `meshy_models`.

[[models-on-the-site]]
=== Models on the site

`gw media add-model <project>/<slug>` puts a model on the site for `model::media:<key>[]` (see
link:authoring.adoc#_3_d_models[Authoring]). It needs Blender (`/Applications/Blender.app`,
`blender` on the PATH, or `GW_BLENDER`) and the model's local-only textured `<slug>.glb`, and it
writes into `site/static/models/<key>/`:

[cols="1,3"]
|===
| `<key>.glb` | the web model: decimated to `--polycount` (150 000) triangles with UVs and
  textures kept, textures at most `--max-texture` (2048) px as JPEG, Draco-compressed (model-viewer
  fetches Google's Draco decoder itself; `--no-draco` for a plain GLB), scaled to its printed size
  in metres so AR shows it life size. About 2–3 MB.
| `<key>.usdz` | the same decimated mesh for AR Quick Look on iOS, checked with `usdcat --loadOnly`
  (left out if it does not load; `--no-usdz` to skip). About 12–14 MB — fetched only when a
  reader taps the AR button.
| `poster.webp` | the model's `images/hero.webp`
| print file | with `--download stl`: the committed `<slug>-print.stl`, or the plate STL for a
  multi-part model; `--download 3mf` the 3MF. Over 25 MB it warns; `--download-polycount 400000`
  decimates the STL with Blender (≈50 bytes a triangle) and reports whether it is still closed.
|===

It then registers `media:<key>` (kind `model`) with `url` (GLB), `ios` (USDZ), `poster`,
`download` and their sizes, the triangle count, the printed size (`dimensions_mm`), the number of
parts, and `ids` (`model: <project>/<slug>`, `meshy_id`). `--key` names it (default: the slug);
running it again for the same model replaces its files; a key that holds something else needs
`--force`. Nothing in the models repository changes. Commit `static/models/<key>/` with the post —
mind the size of large print files in the site repository (GitHub refuses files over 100 MB).

In the app: *Models → (a model) → Add to site* asks for the key, the download and the triangle
counts, and copies the `model::media:<key>[…]` snippet when it is done; *Media → 3-D models* lists
them with their sizes. REST: `POST /api/media/model` (`{"model": "<project>/<slug>", "key": …,
"download": "stl"|"3mf"|"none", "polycount": …, "download_polycount": …, "force": …}`). MCP:
`add_model`.

[[models-gallery]]
=== The website's models gallery

Besides models in posts, the site can have a gallery of them: a card grid with project filters,
and a page per model, `/models/<project>/<slug>/` (every angle render, the description, printed
size, parts, triangle count, the posts that show it, and — where switched on — the interactive 3-D
viewer). Only the models you switch on are shown. The choice lives in the site, in `models.yaml`
beside `site.yaml`:

[source,yaml]
----
title: 3-D models
intro: Figures and props I have made with Meshy.ai and printed.
projects:                          # optional chip titles/descriptions
  ai-force: { title: AI Force }
models:
  - key: lemmings/wizard-lemming   # <project>/<slug> in the models repository
    viewer: true                   # the interactive viewer (needs a web model, below)
    featured: true                 # first in the grid
  - key: ai-force/ai-force-teen
    order: 5                       # before models without an order
    name: AI Force teen            # optional overrides: name, summary, description
----

The pictures come from the models repository, but the build never reads it: switching a model on
copies its renders (`hero`, `front`, `side`, `top`, `plate`, `thumb` — WebP, about 130 kB a model)
and a trimmed `meta.json` (name, summary, description, printed size, parts, triangles; no Meshy
task ids or prompts) into `site/static/model-gallery/<project>/<slug>/`; switching it off removes
that folder. Commit `models.yaml` and `static/model-gallery/` together; the gallery then builds
from the site repository alone. After editing `models.yaml` by hand, or when the repository's
renders change, run `gw models sync-site`.

*Where the grid is.* Put `models::gallery[]` in an article (or page) and that post becomes the
gallery's home — a living article: your own text, then the grid. Then

* `/models/` sends readers to the post (keeping a `#<project>` filter), and is left out of the
  sitemap; take *Models* out of `nav:` in site.yaml if it was there;
* the model pages' breadcrumbs lead back to the post;
* the post's "updated" date follows the newest model put on the website (each model's `added:`
  date in `models.yaml`, set when it is switched on; for older entries, the date the model was
  made) — so it rises in feeds and listings as the gallery grows;
* the post's hero image is used for cards and link previews but not repeated above the grid, and
  its reading time counts only the text.

Without such a post, the build writes the grid at `/models/` (`models.html`, with `models.yaml`'s
`title` and `intro`). The app's Models page has *Make gallery article…* for this (a draft with your
introduction and the block), and links to the gallery article once there is one.
`models::gallery[project=<id>]` shows one project's models anywhere (no chips; it does not make
the post the gallery's home). One gallery per page.

The interactive viewer uses the site's web model for that model — a `kind: model` media entry
whose `ids.model` is the key, made by `gw media add-model <project>/<slug> --download none`. It is
loaded only when a model is opened. A print-file download appears only if that media entry has
one. `gw check` reports a selected model whose pictures are missing and a viewer without a web
model.

[cols="1,3"]
|===
| `gw models list` | the selection, whether each model's pictures are in the site, its web model
| `gw models on <p>/<s>… [--viewer]`, `--project <p>`, `--all` | put models on the website
| `gw models off <p>/<s>…`, `--project <p>` | take them off
| `gw models viewer <p>/<s> --on\|--off` | the interactive 3-D viewer
| `gw models sync-site` | copy the selected models' pictures into the site, remove the rest
|===

In the app, the *Models* page shows "N on the website" and a *Website: All / On / Off* filter;
every card has a *Show on website* switch, a selected project has *Show all on website* / *Hide
all*, and a model's panel has *Show on website* and *Interactive 3-D* (which first makes the web
model with Blender, 10–60 s, when the site has none), and the posts that show it (*In posts*) with
*Add to post…*. *Gallery article* / *Preview* open the gallery's home post (or *Gallery preview*,
`/preview/models/`, when there is none; rebuild the preview to see changes). REST: `GET /api/site-models`; `PUT /api/site-models`
`{"changes": [{"key": "<project>/<slug>" | "project": "<p>", "on": true, "viewer": true,
"featured": true}]}` — keys must be models in the repository.

The pages use the templates `models.html`, `models_grid.html` (the grid, also used by
`models::gallery[]`) and `model.html`, and `static/css/models.css` and
`static/js/models.js` (a site's own files of the same name replace them). Without JavaScript the
grid links to the model pages and the angle thumbnails to the images; with it, project chips
filter the grid (`#<project>` in the address), a card opens the model in a dialog (the address becomes the
model's page, so it can be shared), and the thumbnails or ← → switch the views. Each model page
has its hero render as its Open Graph image; all are in the sitemap.

Stories: add a model to a story like a photo — `gw story add <story> media:<key> --comment "…"` —
and refer to it in the draft as `model::story:<id>[…]`; `gw story draft` writes
`model::media:<key>[…]`.
