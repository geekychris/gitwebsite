= The companion: relays and tool windows
:toc:

Many of the site's browser tools need something a web page cannot do on its own. Examples are reading an
API that sends no CORS headers, opening a TCP connection (Postgres, Redis, a Mode S feed), reading the
Docker socket or a Kubernetes API, or cloning over git smart-HTTP. Each of these used to need its own
relay script (`aviation-relay.py`, `container-relay.py`, `postgres-relay.py`, `git-relay.py`,
`parts-relay.py`, the Kafka CORS relay, a Redis WebSocket bridge). The *companion* replaces all of
them. It is a small gateway built into the gitwebsite app and `gw serve`.

The same app also opens the site's tools in their own windows (the *tool viewer*). Claude uses the
viewer through MCP to show you things: diagrams, plots, simulations.

== Where it runs

* The desktop app and `gw serve` start it on `127.0.0.1:7317`. If that port is taken they fall back
  to 7318–7320. Set a different port with `GW_COMPANION_PORT`, `gw serve --companion-port`, or `port`
  in the settings. It uses its own port, separate from the app's UI port (8790 or a free one).
* `gw serve --no-companion` turns it off for that run. `enabled = false` in the settings turns it off
  for good.
* `<config dir>/server.json` records where the running app listens (`ui_port`, `companion_port`,
  `pid`). `gw mcp` and `gw companion …` read it to find the app.

== Protocol v1 (1.2)

`GET /v1/hello` returns:

[source,json]
----
{"name":"gitwebsite-companion","version":"1.2",
 "capabilities":["relay.http","relay.tcp","relay.docker","relay.kube","relay.git",
                 "relay.lan","relay.ws","relay.s3","view"],
 "paired":false,"scopes":[],"app":false}
----

`app` is true for pages served by the app's own preview. A page should call `/v1/hello` first,
before it shows any "run the relay script" instructions. A capability is listed only while its
relay is turned on. Version `1.2` is protocol v1 plus the LAN, WebSocket and S3 relays, first-use
approvals and more fixed HTTP upstreams (see <<v12>>); everything from `1` is unchanged, so a
page should test for a capability (`relay.lan`), not compare versions.

=== Security on every request

* *Host* must be `127.0.0.1`, `localhost` or `[::1]`, with an optional port. Anything else gets a 403,
  which defeats DNS rebinding.
* *Origin* must be on the allow-list: `https://geekychris.github.io`, `http://127.0.0.1:<port>`,
  `http://localhost:<port>`, `http://[::1]:<port>`, plus any origins you add (`extra_origins`).
  Origins are matched exactly, never by prefix. A request with no Origin is a non-browser client such
  as curl or the CLI. It is allowed, but it still needs a token.
* *CORS*: allowed origins are reflected in `Access-Control-Allow-Origin` (with `Vary: Origin`).
  Preflights (`OPTIONS`) are answered with `Access-Control-Allow-Private-Network: true`, so Chrome's
  Private Network Access lets an https page call localhost. See also <<local-network-access>>.
  Methods allowed: GET, HEAD, POST, PUT, PATCH, DELETE. Requested headers are allowed as asked.
  Exposed response headers include `Content-Range`, `Content-Length`, `Accept-Ranges`, `ETag`,
  `Last-Modified`, `X-Relay-Location`, `X-Amz-Request-Id`, `X-Amz-Version-Id` and the rate-limit
  headers.
* *Tokens*: every endpoint except `/v1/hello` and pairing needs a pairing token with the scope of the
  relay being used. A page can send it three ways:
** `Authorization: Bearer <token>`. In this case the page's Authorization header is _not_ forwarded
   upstream.
** `X-Companion-Token: <token>`. In this case the page's own `Authorization` header _is_ forwarded to
   the upstream: a token for a private git repo, Kafka REST credentials, or a supplier token.
** For WebSockets, the `Sec-WebSocket-Protocol` header: offer `gw-companion.v1, bearer.<token>`. The
   server picks `gw-companion.v1`. If only `bearer.<token>` is offered, it is echoed back. Also offer
   `gw-companion.codes` to get refusals as close codes (see <<ws-refusals>>).
+
Tokens in the query string are never accepted.
* Each token is bound to the origin it was issued to. Only its SHA-256 hash is stored, in
  `<config dir>/companion-tokens.json` (mode 0600).
* Every request except `/v1/hello` is written to the audit log (`<config dir>/companion-audit.log`,
  JSON lines, rotated at 2 MB). Each entry records the time, origin, tool, method, path (without the
  query) and status, plus `close` (the close code of a refused WebSocket) and `note` (e.g.
  `self-revoked`) when they apply.

=== Pairing

`POST /v1/pair` with the body `{"tool":"<slug>","scopes":["relay.tcp", …]}` starts pairing. The
scopes are `relay.http`, `relay.tcp`, `relay.docker`, `relay.kube`, `relay.git`, `relay.lan`,
`relay.ws`, `relay.s3` and `view`. If no scopes are given, the request covers the v1 relays
(`relay.http`, `relay.tcp`, `relay.docker`, `relay.kube`, `relay.git`), not `view` and not the
v1.2 relays: `relay.lan`, `relay.ws` and `relay.s3` reach your network and storage, so a page must
name them.

* Pages from the app's own preview (`http://127.0.0.1:<ui port>`) are paired at once and get
  `200 {"token": …, "scopes": […]}`. So does any page when the companion was started with
  `--companion-auto-approve` (for headless use only).
* Any other page gets `202 {"id", "code", "poll": "/v1/pair/<id>", "expires_in": 300}`. The page
  shows the 6-digit `code`. The app shows a dialog (Allow/Deny) with the origin, the tool, the scopes
  and the same code. The request is also listed on the app's Companion page, and in
  `gw companion pending`. You can approve it with `gw companion approve <code>`, or refuse it with
  `gw companion deny <code>`.
* `GET /v1/pair/<id>`, sent from the same origin, long-polls for up to 50 s. Every outcome is a quiet
  success status, so a denied or expired request does not log a resource error in the page's console:
+
[cols="1,3"]
|===
| Status | Body

| `202` | `{"status":"pending","pending":true}`: poll again.
| `200` | `{"status":"approved","token":…,"scopes":[…]}`
| `200` | `{"status":"denied","denied":true,"error":"pairing denied"}`
| `200` | `{"status":"expired","expired":true,"error":…}`: expired, already collected, or polled from a
          different origin.
|===
+
Go by `status` (or by which of `token`, `denied`, `expired` is present), not by the HTTP status
alone. Earlier builds answered `403` for denied and `404` for expired; a page should keep treating
those the same way, so it works with both.
* Pairing again from the same origin and tool replaces the old token. To revoke a token, use the
  Companion page, `gw companion revoke <id or origin>`, or `DELETE /api/companion/tokens/<id>`.
* `DELETE /v1/token`, authenticated with the token itself (any scope, from the origin it was issued
  to), revokes it: the page's "Forget". It returns `200 {"revoked":1,"id":…}`, or `401` for an unknown
  or already revoked token, and is written to the audit log with the note `self-revoked`.

[[local-network-access]]
=== Chrome's Local Network Access prompt

Chrome (Local Network Access, the successor to Private Network Access) asks the visitor for
permission before an https page such as `https://geekychris.github.io` may reach `127.0.0.1`. The
first request to the companion from the site, including the `/v1/hello` probe, triggers the prompt
("… wants to access other apps and services on this device"); until it is allowed, every request
fails like a network error, exactly as if the app were not running. So pages should:

* probe lazily, on a user action (pressing *Connect* or *Use the gitwebsite app*, choosing a live
  source), not on page load — otherwise every visitor, most without the app, gets a permission
  prompt they did not ask for;
* after a failed probe, say "the gitwebsite app isn't running, or Chrome blocked access to this
  computer" and point at the site-settings toggle ("Local network access", in the padlock menu);
* treat `http://127.0.0.1:*` and `http://localhost:*` pages (the app's own preview) as exempt:
  they are not prompted, so probing them eagerly is fine.

The app's Companion page carries the same hint for users: allow the prompt in Chrome when a site
tool first connects.

`GET /v1/status` (with any valid token) describes the relays: upstream ids, which user upstreams are
configured, which supplier secrets are present, the TCP allow-list, the Docker socket, the Kubernetes
contexts and the git hosts. It never shows a secret or a token.

== Relays

=== HTTP: `/v1/relay/http/<upstream>/<path>`

The relay only reaches a fixed set of upstreams, so it is never an open proxy. The path must use
URL-safe characters only. It may not contain `..`, `.` segments, `//`, `@`, a backslash or a scheme,
and the resulting host must be the upstream's own. Cookies and the page's Origin are never forwarded.

[cols="1,2,1"]
|===
| Upstream | Goes to | Methods

| `adsblol`, `adsbfi`, `opensky`, `awc` | api.adsb.lol, opendata.adsb.fi, opensky-network.org, aviationweather.gov | GET (cached for 2 s)
| `noaa-coops`, `ndbc`, `pskreporter`, `open-meteo` (1.2) | api.tidesandcurrents.noaa.gov, www.ndbc.noaa.gov, retrieve.pskreporter.info, api.open-meteo.com | GET (cached for 2 s)
| `open-elevation` (1.2) | an alias of `open-meteo` (api.open-meteo.com, e.g. `open-elevation/v1/elevation?latitude=…&longitude=…`), *not* api.open-elevation.com | GET (cached for 2 s)
| `receiver` | your ADS-B receiver (setting `receiver`, e.g. `http://piaware.local:8080`) | GET (cached for 2 s)
| `digikey`, `mouser`, `nexar`, `nexar-id` | the parts suppliers' APIs | GET, POST (bodies up to 64 KB, header allow-list)
| `kafka-rest`, `redpanda-proxy` | your Kafka REST proxy or Redpanda HTTP Proxy (settings) | GET, POST, PUT, DELETE; POST with `X-Method-Override: GET` becomes a GET with a body
| `redpanda-admin` | the Redpanda Admin API (setting) | GET (and POST with override to GET)
|===

The configured bases (`receiver`, `kafka_rest`, `redpanda_proxy`, `redpanda_admin`) are
*scheme://host[:port] only*: the page's path is joined on, so `receiver/data/aircraft.json` with
`receiver = "http://piaware.local:8080"` reaches `http://piaware.local:8080/data/aircraft.json`. A
base with a path still works: with `http://piaware.local:8080/tar1090`, both
`receiver/data/aircraft.json` and `receiver/tar1090/data/aircraft.json` reach
`…/tar1090/data/aircraft.json` (a request path that already starts with the base's path is not
doubled). Bases with a query, a fragment or `user:password@` are refused; the Companion page
checks this when you save, and notes a base that has a path.

The relay keeps the rate-limit headers (`X-Rate-Limit-Remaining`, `X-RateLimit-*`, `Retry-After`).
It adds `X-Relay-Upstream` and `X-Relay-Cache` to each response.

*Supplier secrets.* The relay can sign supplier requests with stored secrets, the same way
`parts-relay.py` did:

* `digikey_client_id` and `digikey_client_secret`: the relay gets a Digi-Key OAuth token and sends it
  with `X-DIGIKEY-Client-Id`.
* `mouser_api_key`: added as `apiKey=`.
* `nexar_client_id` and `nexar_client_secret`: the relay gets a Nexar token.

The secrets live in the macOS Keychain (service `gitwebsite-companion`). The environment variables
`DIGIKEY_CLIENT_ID` and so on take precedence. A companion run with a non-default config directory
(`GW_CONFIG_DIR` pointing anywhere but your real one: a scratch or test instance) never reads or
writes the Keychain: its secrets live in `<config dir>/companion-secrets.json` (mode 0600), so it
cannot see or overwrite your real supplier keys. `/api/companion` reports which store is in use
(`secrets_store`: `keychain:gitwebsite-companion` or `file:<path>`).

*Testing supplier relays.* `upstream_override` in `companion.toml` points fixed upstreams at a mock:

[source,toml]
----
[upstream_override]
digikey = "http://127.0.0.1:9911"     # also used for its OAuth token endpoint
nexar-id = "http://127.0.0.1:9911"
----

It is honoured only for a non-default config directory, or when `GW_COMPANION_TEST_UPSTREAMS=1` is
set; for your real config it is ignored with a warning. It cannot be set through the app's API. E2E:
`GW_CONFIG_DIR=$(mktemp -d) gw companion secret set digikey …`, write the override, then
`GW_CONFIG_DIR=… gw serve --port 8890 --companion-port 7400 --companion-auto-approve` (ports other
than your running app's). Set them in the app's Companion page or with
`gw companion secret set digikey`. You can see whether each secret is present, but no API ever
returns its value.

=== TCP over WebSocket: `/v1/relay/tcp?target=host:port[&mode=text]`

The relay copies bytes, unchanged, between the WebSocket and a new TCP connection. Frames are binary
in both directions. With `mode=text`, the server sends text frames instead, for the Mode S AVR raw
feed. The target must be on `tcp_allow`, which by default is `127.0.0.1:5432` and `127.0.0.1:6379`;
add entries such as a Pi's `:30005` Beast or `:30002` raw port. Since 1.2, a paired page's first
connection to a target that is not listed but is on the LAN (see <<lan-def>>) waits while the app
asks you (<<approvals>>); allowing adds `host:port` to `tcp_allow`. Public targets (for example
APRS-IS `rotate.aprs2.net:14580`) are never offered for approval: add them by hand. `localhost`, `127.0.0.1` and `::1`
count as the same host. Every WebSocket gets its own TCP connection, so each Postgres session is its
own backend. This relay is used by the Postgres playground, the Redis client and the Mode S feeds.

[[ws-refusals]]
*Refusals.* A browser cannot read the HTTP status of a failed WebSocket upgrade, so a page that
offers the extra subprotocol `gw-companion.codes` (for example
`new WebSocket(url, ['gw-companion.v1', 'gw-companion.codes', 'bearer.' + token])`) gets refusals
after the upgrade instead: the server accepts it selecting `gw-companion.codes` (on success it never
selects that one, so `ws.protocol === 'gw-companion.codes'` at `open` means a refusal follows) and
closes at once with an application close code and a reason (at most 123 bytes):

[cols="1,3"]
|===
| Code | Meaning

| `4400` | bad request (e.g. no `?target=`)
| `4401` | not paired: no token, or an unknown or revoked one for this origin — pair again
| `4403` | not allowed: the token lacks the `relay.tcp` scope, the target is not on `tcp_allow`, or the relay is turned off
| `4502` | the companion could not connect to the target (refused, unreachable, or timed out)
|===

Without `gw-companion.codes`, refusals are HTTP errors before the upgrade (`400`, `401`, `403`,
`502`, `503`, `504`), as in the first release. Host and Origin failures are always a plain HTTP
`403` before any upgrade, whatever is offered: a page from a foreign origin learns nothing.

=== Docker: `/v1/relay/docker/<api path>`

This relay reads the Docker Engine API over the local socket. It uses `docker_host` if set, then
`$DOCKER_HOST` (`unix://`), then the first socket it finds: `/var/run/docker.sock`,
`~/.rd/docker.sock` (Rancher Desktop), `~/.docker/run/docker.sock`, Colima, then OrbStack. The
behaviour is the same as `container-relay.py`:

* GET only. Any other method gets 405.
* Only an allow-list of read endpoints is forwarded: `_ping`, `version`, `info`, `system/df`,
  `events`, the container and image lists, a container's `json`, `logs`, `stats`, `top` and
  `changes`, image `json` and `history`, volumes and networks.
* `exec`, `attach`, `archive`, `export` and `images/get` are refused, and so are upgrade requests.
* Streaming reads (`follow=1`, `stats`, `events`) pass through with no timeout.
* `GET /v1/relay/docker` reports the socket and a ping.

=== Kubernetes: `/v1/relay/kube/<context>/<api path>`

This relay reaches a Kubernetes API through your kubeconfig (`kubeconfig`, else `$KUBECONFIG`, else
`~/.kube/config`) and a named context. Percent-encode context names that contain `/`. The kubeconfig
is read but never written, and its current context is never changed. Credentials stay in the
companion:

* client certificates
* bearer tokens and `tokenFile`
* basic auth
* `exec` plugins such as `aws eks get-token` or `gke-gcloud-auth-plugin`; their tokens are cached
  until shortly before they expire.

`tls-server-name` and `insecure-skip-tls-verify` are honoured. `auth-provider` is not supported; use
`kubectl proxy` instead.

The relay is GET only. Watches and log follow stream through. Secrets are refused, as are `exec`,
`attach`, `portforward` and the `proxy` subresources. `GET /v1/relay/kube` lists the contexts with
their server and auth kind, but no credentials.

=== Git: `/v1/relay/git/<host>/<repo>/(info/refs|git-upload-pack|git-receive-pack)`

This is a CORS proxy for isomorphic-git. Set `corsProxy` to `http://127.0.0.1:7317/v1/relay/git`,
and send the token in an `X-Companion-Token` header through isomorphic-git's `headers` option. The
relay works like `git-relay.py`:

* Only these requests are relayed: `GET info/refs?service=git-upload-pack` and
  `POST git-upload-pack`.
* Hosts must be on the allow-list: github.com, gitlab.com, codeberg.org, bitbucket.org, plus
  `git_hosts`. The upstream is always https.
* Push (`git-receive-pack`) is refused unless `git_allow_push = true`.
* `info/refs` responses are read whole from the git host and sent with a `Content-Length`;
  `git-upload-pack` (the packfile) is streamed. isomorphic-git stops reading the ref advertisement
  at its final flush-pkt and releases the reader without draining the body; when that body was
  streamed (chunked), Chrome could list the request as `net::ERR_ABORTED` after its `200`. It was
  harmless (the clone carried on), and sending `info/refs` whole avoids it.

[[v12]]
=== LAN devices: `/v1/relay/lan/<host[:port]>/<path>` (1.2, scope `relay.lan`)

HTTP(S) to a device on your local network: Home Assistant's REST API, Shelly, Tasmota, Hue, Roku
ECP, WebHDFS/HttpFS, MinIO, Samsung Tizen REST.

* `host` is an IP, a name or an mDNS `.local` name; IPv6 in brackets (`[fe80::1]:80`). The port
  defaults to 80, or 443 with `?tls=1`.
* `?tls=1` connects with https. `?insecure=1` (with `tls=1`) accepts a self-signed certificate
  (Hue, webOS, Tizen). Both are removed from the query sent upstream; the rest of the query is
  passed as sent.
* Methods: GET, HEAD, POST, PUT, PATCH, DELETE. Bodies up to 64 MB, streamed both ways; no
  overall timeout, so event streams work.
* Request headers passed: `Content-Type`, `Accept`, `Range`, the vendor headers
  `hue-application-key` and `X-Auth-Token`, the AWS headers `X-Amz-Target`, `X-Amz-Date`, `X-Amz-Security-Token` and `X-Amz-Content-Sha256` (for DynamoDB Local and LocalStack), and `Authorization`, taken from
  `X-Upstream-Authorization` (so it does not clash with the companion's own
  `Authorization: Bearer`). When the token comes in `X-Companion-Token`, the page's own
  `Authorization` is passed as in v1 (`X-Upstream-Authorization` wins if both are sent). Cookies,
  the Origin and the pairing token never go upstream.
* Response headers kept: `Content-Type`, `Content-Length`, `Content-Range`, `Accept-Ranges`,
  `ETag`, `Last-Modified`, `Retry-After`, `Server`, plus `X-Relay-Upstream: lan`. Redirects are not
  followed; a `Location` comes back as `X-Relay-Location` (and is dropped, so the browser doesn't
  follow it around the relay — for WebHDFS's two-step create, read `X-Relay-Location` and send
  the second request through the relay too).
* The host must be on `lan_hosts`. The first request from a paired page to a host that isn't
  waits while the app asks you; allowing adds the *host* (any port) to `lan_hosts`. Enter
  `host:port` by hand for a tighter entry.

[[lan-def]]
*What counts as the LAN.* RFC 1918 (`10/8`, `172.16/12`, `192.168/16`), link-local
(`169.254/16`, `fe80::/10`), loopback (`127/8`, `::1`) and IPv6 unique-local (`fc00::/7`, the v6
RFC 1918). Carrier-grade NAT (`100.64/10`, Tailscale) is not. A public address is refused at
once (`403`, no prompt), including in `lan_hosts`. Names, `.local` included, are resolved and
*every* address must be on the LAN; the connection is then made only to checked addresses — the
LAN HTTP client re-checks each lookup at connect time, and the WebSocket relay connects to the
address it checked — so a name cannot be rebound to a public address between the check and the
connection. A name other than `localhost` that resolves to loopback is refused (a rebinding
trick); use `127.0.0.1` or `localhost`. The companion's and the app's own ports on this machine
(its own, the UI port, 7317–7320 and 8790) are always refused, so a page cannot reach the app's
REST API through a relay. Insecure TLS is allowed only for LAN targets.

=== WebSockets: `/v1/relay/ws?target=<ws(s)://host[:port]/path>[&insecure=1]` (1.2, scope `relay.ws`)

A WebSocket proxy: LG webOS SSAP (`ws://tv:3000`, `wss://tv:3001` with `insecure=1`), the Home
Assistant WebSocket API, Neo4j over WebSocket, the Samsung Tizen remote (`wss://tv:8002`).

* A LAN target uses the same `lan_hosts` allow-list and the same first-use approval as relay/lan.
* A public target must be `wss://` and its host (or `host:port`) on `ws_allow`, which you edit by
  hand (no prompt). `insecure=1` is refused for it, and `ws://` to a public host always is.
* Text and binary frames pass through unchanged; pings are answered at each end; a close (with its
  code and reason) is passed on. 16 MB per message.
* Authentication as for relay/tcp: `Sec-WebSocket-Protocol: gw-companion.v1, bearer.<token>`, and
  `gw-companion.codes` for close-code refusals (4400 bad target, 4401 not paired, 4403 not
  allowed / public / denied / scope, 4502 cannot connect, TLS failed or handshake failed).
* Other subprotocols the page offers (e.g. `mqtt`) are offered upstream without the companion's
  own; if the upstream picks one, it is picked for the page too (`ws.protocol === 'mqtt'`), else
  `gw-companion.v1`. The page's Origin is not sent upstream.

=== S3: `/v1/relay/s3/<profile>/<bucket>/<key…>` (1.2, scope `relay.s3`)

S3-compatible storage (AWS S3, MinIO, R2, B2, Ceph, Garage), signed by the companion with
Signature Version 4 from a named *profile*: endpoint (`scheme://host[:port]`, no path), region,
path-style (`endpoint/bucket/key`, for MinIO and most self-hosted stores) or virtual-host style
(`bucket.endpoint/key`), and `insecure` (self-signed, LAN endpoints only). The access key id and
secret are in the secret store as `s3:<profile>:access_key_id` and
`s3:<profile>:secret_access_key`; no API returns them.

[cols="2,1,3"]
|===
| Request | S3 operation | Notes

| `GET /v1/relay/s3` | — | `{"profiles":[{"name","endpoint","region","path_style","insecure","credentials":true}]}` — never secrets
| `GET …/<p>` | ListBuckets |
| `GET …/<p>/<bucket>?prefix=&delimiter=&continuation-token=&start-after=&max-keys=&fetch-owner=&encoding-type=` | ListObjectsV2 | `list-type=2` is added; other parameters are refused (400)
| `GET …/<p>/<bucket>/<key>` | GetObject | `Range`, `If-Match`, `If-None-Match`, `If-(Un)Modified-Since` passed; `versionId`, `partNumber`, `response-content-*` allowed; streamed
| `HEAD …/<p>/<bucket>/<key>` | HeadObject |
| `PUT …/<p>/<bucket>/<key>` | PutObject | needs a `Content-Length` (send a Blob/ArrayBuffer; chunked → 411), at most 100 MB (413), streamed with `UNSIGNED-PAYLOAD`; `Content-Type`, `Content-MD5`, `Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language`, `Expires` and `x-amz-meta-*` passed
| `DELETE …/<p>/<bucket>/<key>[?versionId=]` | DeleteObject | waits for your confirmation in the app (<<approvals>>) unless `s3_confirm_delete = false`; a denial is `403`
| `POST …/<p>/presign` `{"method":"GET\|PUT\|HEAD","bucket":…,"key":…,"expires":900}` | presigned URL | `{"url","method","expires"}`; `expires` 1–604800 s (default 900); DELETE refused. The URL goes straight to the store (its CORS rules apply)
|===

Responses keep `Content-Type`, `Content-Length`, `Content-Range`, `Accept-Ranges`, `ETag`,
`Last-Modified`, `Content-Disposition`, `Content-Encoding`, `x-amz-request-id`,
`x-amz-version-id`, `x-amz-delete-marker`, `x-amz-storage-class` and `x-amz-meta-*`, and add
`X-Relay-S3-Op`. S3's own XML errors pass through with their status. Other operations (bucket
create/delete, ACLs, policies, multipart) are refused (`405`). Keys may not contain `.` or `..`
segments or control characters. The signer is tested against AWS's published SigV4 test suite and
the S3 API reference's examples.

[[approvals]]
=== First-use approvals (1.2)

When a paired page asks for a LAN host that is not on `lan_hosts` (relay/lan, relay/ws), a LAN TCP
target not on `tcp_allow`, or an S3 deletion, the request *waits* (up to 90 s) while the app shows
a dialog with the tool, the page's origin, what it asked for and a 6-digit code. The request is
also listed on the Companion page and in `gw companion approvals`; decide it with
`gw companion approve <code>` / `gw companion deny <code>`, or by target with
`gw companion lan approve <host>` / `gw companion tcp approve <host:port>`.

* Allowed: the request goes ahead, and a LAN host or TCP target is added to its allow-list
  (saved in `companion.toml`). An S3 deletion approves that one deletion only.
* Denied: `403` (WebSocket close `4403`) with "denied"; the same target from the same origin is
  refused at once, without asking again, for 5 minutes.
* Undecided after 90 s: `403` / `4403` with "waiting for approval in the app (code …)"; the
  question stays open (5 minutes) and a retry waits on the same one.
* Concurrent requests for the same target share one question. With `auto_approve`
  (`--companion-auto-approve`, headless only), first-use requests and S3 deletions are approved
  too.

Every decision is in the audit log (`{"event":"approval","kind","target","origin","tool",
"decision","by"}`), and so are settings changes (`{"event":"settings","keys"}`) and secret changes
(`{"event":"secret","names","action"}`, names only).

=== Testing a site tool against v1.2

Run a scratch companion (its own config directory: file-backed secrets, never the Keychain; ports
away from the real app's 8790/7317):

----
export GW_CONFIG_DIR=$(mktemp -d)
gw serve --port 8891 --companion-port 7401            # prompts: answer with the CLI below
# or, headless, approving pairing and first-use requests automatically:
gw serve --port 8891 --companion-port 7401 --companion-auto-approve

# in another shell, with the same GW_CONFIG_DIR (and GW_APP_PORT=8891):
gw companion approvals                 # first-use requests waiting
gw companion approve 123456            # a pairing or first-use code
gw companion lan add 127.0.0.1         # pre-allow a fake device
gw companion ws add echo.websocket.org # a public wss:// host
gw companion s3 add minio --endpoint http://127.0.0.1:9000 --region us-east-1 --path-style
gw companion secret set s3:minio:access_key_id --value minioadmin
gw companion secret set s3:minio:secret_access_key --value minioadmin
----

Point the page's companion base at `http://127.0.0.1:7401`. Fakes on `127.0.0.1` count as LAN
devices. The repository's e2e tests (`crates/gw/tests/companion_v12.rs`,
`companion_cli_e2e.rs`) show fakes for a LAN device (plain and self-signed TLS), a WebSocket echo
(ws and self-signed wss) and an S3 server that verifies SigV4.

=== Deviations from the v1.2 draft spec

These were decided while building v1.2; the URL shapes are as in the draft.

* Pairing with no scopes does not include `relay.lan`, `relay.ws` or `relay.s3`; ask for them.
* A first-use request waits up to 90 s in place, then answers `403` "waiting for approval" (the
  question stays open); a denial is remembered for 5 minutes.
* A LAN approval allows the host on any port (`lan_hosts` entry `host`); `host:port` entries can
  be added by hand.
* relay/lan also allows HEAD, passes `Range`, and passes the page's `Authorization` when the token
  is in `X-Companion-Token` (as the v1 relays do). Redirects come back with `X-Relay-Location`.
* LAN includes IPv6 unique-local `fc00::/7`; names (other than `localhost`) that resolve to
  loopback, and the companion's/app's own ports, are refused.
* TCP first-use prompts only for LAN targets; public TCP targets must be added by hand.
* S3: `GET /v1/relay/s3/<p>` is ListBuckets; PutObject needs a `Content-Length` (no chunked
  uploads); `s3_confirm_delete` can turn the delete confirmation off; `--companion-auto-approve`
  approves deletions.
* Upstreams: no `wsprnet` (wspr.live already sends CORS headers); `open-elevation` is an alias of
  `open-meteo` (api.open-meteo.com), not api.open-elevation.com.

== Tool viewer

The app's REST API opens tools in windows:

[cols="1,3"]
|===
| Request | Does

| `POST /api/view` | Body: `{"tool":"<slug>", "params":{…}, "example":"…", "hash":"tab", "state":{…}, "title":"…", "window":"reuse\|new\|<id>", "chrome":false}`. Opens `http://127.0.0.1:<ui port>/tools/<slug>/?<params>&example=…&bare=1#<hash>` in a native window titled with the tool's name (or `title`). `reuse`, the default, navigates the window already showing that tool. `state` is packed into the site kit's `?s=` as `j` + base64url JSON. Returns `{opened, window:{id,tool,title,url}, url}`.
| `GET /api/view` | The open tool windows.
| `DELETE /api/view/<id>` | Closes a window.
| `POST /api/view/<id>/screenshot` | A PNG of the page, taken with WKWebView's snapshot (macOS). Returns 501 elsewhere.
|===

Links that leave the preview open in the default browser. Closing a tool window really closes it;
only the main window hides to the menu bar. A page with a `view` token can ask for a window too, with
`POST /v1/view` (same body).

Under `gw serve` there is no app to make windows, so `POST /api/view` opens the URL in the default
browser, and listing, closing and screenshots are unavailable.

For a tool to fill the window, its page must honour `?bare=1`: no site header, footer or help chrome.
That is the site kit's job.

== Tool catalogue

`GET /api/tools[?category=&q=]` and `GET /api/tools/<slug>` read the site's tool pages
(`content/tools/*.adoc`, `:type: tool`). For each tool they return:

* the slug, title, summary, category and tags
* the URL parameters from the "Linking to an example" table: name, meaning and an example; when a
  page has no table, the parameters mentioned in its Sharing text and example links
* the `?example=` presets, from a table or a list
* the tabs ("Add a tab after `#`: …")
* example links, and (in `info`) the page's help text

`gw tools list|info|open|index` does the same from the command line. `gw tools index` writes
`skills/show-with-tools/tools-index.md`, the "which tool for which rendering" table used by the
skill. `scripts/gen-tools-skill-index` regenerates it, and so does `scripts/install-skills.sh`.

== MCP tools

`gw mcp` finds the running app through `server.json` (or `GW_APP_PORT`, else 8790) and adds these
tools:

[cols="1,3"]
|===
| Tool | Does

| `tools_list` | The catalogue: slug, title, category, summary, tags, parameter names, presets and tabs (filter with `category` and `q`).
| `tool_info` | One tool: its parameters with meanings, the presets and what each shows, its tabs, links and help text.
| `tool_open` | `{slug, params, example, hash, title, window}` → opens the window and returns `window`, `url` and `public_url`. It checks the preset name. If the app isn't running, it returns `public_url` to give the user instead.
| `tool_windows`, `tool_close` | List and close tool windows.
| `tool_screenshot` | The window as an MCP image (PNG).
| `companion_status` | App and gateway status, the relays, paired tools, pending requests, and which secrets are present.
|===

The `show-with-tools` skill teaches Claude when to use these tools, and how.

== Settings

The settings live in `<config dir>/companion.toml`, beside `config.toml` (see `gw config show`). You
can edit them on the app's *Companion* page or with `gw companion set <key> <value>` (values may be
JSON; `relays.git false` sets one relay), or by hand.

[source,toml]
----
enabled = true
port = 7317
extra_origins = []                       # more page origins
tcp_allow = ["127.0.0.1:5432", "127.0.0.1:6379"]
lan_hosts = []                           # relay/lan + LAN ws: "hue.local", "192.168.1.20:8123"
ws_allow = []                            # public wss:// hosts for relay/ws
s3_confirm_delete = true
receiver = ""                            # ADS-B receiver web base
kafka_rest = ""
redpanda_proxy = ""
redpanda_admin = ""
git_hosts = []
git_allow_push = false
docker_host = ""                         # empty: auto-detect
kubeconfig = ""                          # empty: $KUBECONFIG or ~/.kube/config
auto_approve = false
# [upstream_override]                    # testing only, see "Testing supplier relays"
# digikey = "http://127.0.0.1:9911"
[relays]
http = true
tcp = true
docker = true
kube = true
git = true
lan = true
ws = true
s3 = true

[s3_profiles.minio]                      # credentials: gw companion secret set s3:minio
endpoint = "http://nas.local:9000"
region = "us-east-1"
path_style = true
insecure = false
----

The Companion page shows:

* the gateway's status and URL
* a hint about Chrome's Local Network Access prompt
* pending pairing requests (Allow/Deny), with the tool and the page's origin
* pending first-use approvals (LAN hosts, TCP targets, S3 deletions; Allow/Deny)
* paired origins and tools (Revoke)
* relay toggles, allow-lists (TCP, LAN hosts, public wss hosts) and upstream URLs
* S3 profiles (add, remove, set credentials — write-only; shown as present or absent)
* the Docker socket and Kubernetes contexts it found
* supplier secrets, shown as present or absent (Set or Remove; values are never shown), and where
  they are kept
* the audit log (with WebSocket close codes and self-revocations)

The app's pairing dialog is titled with the tool's name and shows the tool, the page's origin, each
requested scope with what it allows, and the code.

Changes to companion state through `/api/companion/*` and `/api/view` are refused from any page whose
Origin differs from the app's own. A changed port takes effect after a restart.

== Limits

* The gateway binds 127.0.0.1 only. There is no option to expose it to a network.
* `gw companion …` finds the app through `<config dir>/server.json` or `GW_APP_PORT`; with a
  scratch `GW_CONFIG_DIR` it never falls back to 8790 (the real app's port).
* There is no TLS. Traffic between a page and the companion is plain HTTP or WebSocket on localhost,
  so the Postgres and Redis protocols are unencrypted there, as they were with the scripts.
* Screenshots work only in the macOS app. On other platforms they return 501.
* The Kubernetes relay does not support `auth-provider` contexts or client certificates returned by
  exec plugins.
* The kubeconfig's YAML is read with serde_yaml, and multiple `$KUBECONFIG` files are merged with the
  first file winning.
* Linux builds have no persistent secret store (the keychain feature is macOS and Windows only). Use
  the environment variables instead (or, for a non-default config directory, the secrets file).
