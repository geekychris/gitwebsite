= Writing content
:toc:

All content is AsciiDoc. A post is a header, a blank line, and the body.

== The header

[source,asciidoc]
----
= Building a router sled for the workbench
:type: update
:date: 2026-10-12
:project: workbench
:areas: woodworking, cnc
:tags: jig, router, plywood
:summary: A sled that turns the router into a flattening machine — and the three things I got wrong first.
:hero: media:sled-overview
:repo: https://github.com/octocat/workbench-cad
:status: draft
----

[cols="1,3",options="header"]
|===
| Attribute | Meaning

| `:type:` | `article`, `project`, `update`, `app`, `playground`, `page`. Optional: inferred from the folder.
| `:date:` | `YYYY-MM-DD`. Required for posts (articles and updates).
| `:updated:` | Date of a significant revision; shown beside the date.
| `:areas:` | Comma-separated areas (`gw areas` lists them). See <<information-architecture.adoc#,Information architecture>>.
| `:tags:` | Comma-separated free-form tags.
| `:project:` | For updates and project-related articles: the project's slug.
| `:summary:` | One or two sentences for cards, the feed, search, and social previews.
| `:hero:` | Lead image: `media:<key>`, a path inside a bundle (`photos/front.jpg`), or a URL.
| `:hero-crop:` | The part of the hero image a card shows: `left, top, width, height` in percent of the image (e.g. `10, 20, 80, 45`). Cards are 16:9 and otherwise show the image's middle. Set it in the app: *Tile image* in the editor drags a 16:9 box over the image and previews the card.
| `:status:` | `draft` (default for new items) or `published`.
| `:visibility:` | `public` (default) or `unlisted`.
| `:featured:` | Present (no value needed) to feature on the home page.
| `:pinned:` | Pin to the top of the home page, above Featured. A number (`:pinned: 1`) orders the pins, lowest first; pins without one follow, newest first.
| `:repo:` | Source repository, linked from the page.
| `:url:` | Apps: where the live app runs.
| `:embed:` | Apps: `true` to embed the live app in the page.
| `:source:` | Registry id this content came from (imports set this).
| `:slug:` | Override the URL slug (default: from the file name).
| `:works-with:` | Tools: other tools this one is used together with, each with a reason — see <<works-with>>.
|===

Create items with the CLI rather than by hand — it puts files in the right place and
validates areas:

[source,console]
----
gw new article "Why my first jig failed" --area woodworking --tag jig
gw new project "Workbench" --area woodworking --area cnc
gw new update "Router sled" --project workbench --bundle
gw new app "boingtrace" --area amiga --url https://example.org/boingtrace
gw new playground "Bezier curves" --area engineering
gw release articles/why-my-first-jig-failed      # mark published
----

== Bundles: text with its own images

`--bundle` makes `slug/index.adoc` instead of `slug.adoc`. Everything else in the folder is
copied beside the page, so images can be referenced by relative path:

[source,asciidoc]
----
image::front.jpg[The finished bench, front view]
----

Projects are always bundles (`content/projects/<slug>/index.adoc`), with updates in
`updates/`.

== Images and video

Three ways to show media, all usable together:

. *In a bundle* — `image::photo.jpg[Alt text]`. Simple, versioned with the text, served from
  GitHub Pages. Keep files small (resize to ~2000 px wide; JPEG for photos).
. *Any URL* — `image::https://example.org/x.jpg[Alt text]`.
. *The media library* — `image::media:sled-overview[Alt text]`. Keys are defined in
  `site/media.yaml` (`gw media add`, or uploaded with `gw smugmug upload`). Use this for
  anything hosted on SmugMug, and for images used on several pages. Video works the same way:
  `video::media:sled-demo[width=100%]`.

An unknown `media:` key fails the build, so broken images cannot be published.

== 3-D models

A 3-D model goes in with the `model::` block macro, on a line of its own:

[source,asciidoc]
----
model::media:wizard-lemming[Wizard lemming, download=true]
model::media:rock-star-lemming[Rock star lemming, download=true, height=420]
model::media:ai-force-big-brain-textured[AI Force big brain, download=false, autorotate=false]
----

It renders Google's https://modelviewer.dev[`<model-viewer>`] (loaded from jsDelivr as a module,
only on pages that have a model): drag to turn it, pinch or scroll to zoom, it turns slowly by
itself, and on a phone *View in your space* places it in the room at its printed size (AR Quick
Look with the USDZ on iPhone and iPad, Scene Viewer on Android, WebXR). Until it loads — and for
readers without JavaScript — the poster image shows. The caption carries the name, the printed
size and parts, and a *Download STL (32 MB)* link when there is a download.

Attributes (all optional):

[cols="1,3"]
|===
| first positional | caption (default: the library entry's caption, the model's name)
| `download=true\|false\|<path>` | offer the print file; default true when the entry has one
| `ar=true\|false` | the AR button (default true)
| `autorotate=true\|false` | turn slowly until touched (default true)
| `height=480` | viewer height: `480` (px), `480px`, `30rem`, `60vh`; default `min(72vh, 30rem)`
| `reveal=auto\|interaction` | `interaction` waits for a click before downloading the model
| `orbit="30deg 75deg 105%"` | the starting camera angle (model-viewer `camera-orbit`)
| `alt=`, `poster=`, `ios=` | alt text; poster image and USDZ for a direct path
|===

Models come from the media library (kind `model`). Make one from the Meshy models repository with
`gw media add-model <project>/<slug> [--download stl|3mf|none]` or *Models → (a model) → Add to
site* in the app (see link:integrations.adoc#models-on-the-site[Integrations]). A model can also
be a file beside the post or a site path or URL — `model::robot.glb[]` (a `robot.usdz` and
`robot.webp` beside it are picked up), `model::/models/x/x.glb[poster=/models/x/x.webp]`.

Adding and removing models without typing the macro:

* *In the app's editor*: *3-D models* opens a panel listing the post's models — change a caption or
  the download, jump to the line, *Remove*, or *Add model…*: pick from the Meshy models repository
  (a model without a web model gets one made with Blender first, 10–60 s). The new block goes after
  the paragraph the cursor is in, or at the end. The panel edits the text; *Save* keeps it.
* *On the Models page*: a model's panel lists the posts that show it (*In posts*, each with ✕ to
  take it out) and has *Add to post…* (at the end of the chosen post; saved at once).
* *CLI*: `gw models in <post>`, `gw models add <post> <model> [--caption …] [--download
  true|false] [--after-line N]`, `gw models remove <post> <model>|#n` — `<model>` is a media key or
  `<project>/<slug>`. *REST*: `GET /api/items/{id}/models`, `POST /api/items/{id}/models`
  `{"action": "add"|"remove"|"update", "model": …, "index": …, "caption": …, "download":
  true|false|null, "after_line": …}`. *MCP*: `post_models`, `post_add_model`, `post_remove_model`.

The whole models gallery goes in a post with `models::gallery[]` on a line of its own (or
`models::gallery[project=lemmings]` for one project's models, without the filter chips;
`chips=false` hides the chips) — see link:integrations.adoc#models-gallery[the website's models
gallery].

`gw check` reports an unknown key, a key that is not a model, `download=true` on a model without a
download file, and bad attribute values; the page shows a "3-D model unavailable" notice in their
place. In a story draft use `model::story:<id>[]` (see link:stories.adoc[Stories]). WordPress
cross-posts get the poster linked to the download instead of the viewer.

== Code playgrounds

Mark a source block as a playground and readers can edit and run it in the browser:

[source,asciidoc]
....
.Try changing the gravity
[source.playground,javascript]
----
console.log('hello');
----
....

Languages (the runtime for each loads from jsDelivr the first time a reader presses *Run*):

[cols="1,3",options="header"]
|===
| Language id | Runs on

| `javascript` | A Web Worker; `console.log` output is shown.
| `python` | Pyodide. Imports such as `numpy` load automatically; `# pip: pkg` installs pure-Python packages.
| `c`, `cpp` | YoWASP Clang (LLVM as WebAssembly, ~50 MB first use) → `wasm32-wasi`, run with a WASI shim. C++ has no exceptions (`-fno-exceptions`).
| `lua` | Lua 5.4 (wasmoon).
| `ruby` | CRuby 3.4 (ruby.wasm) with the standard library; state persists between runs on a page.
| `sql` | SQLite (sql.js); one database shared by every `sql` block on the page, results shown as tables.
| `duckdb` | duckdb-wasm; blocks share a database, and *Load file…* imports a local CSV/Parquet/JSON as a table.
| `prolog` | SWI-Prolog; lines starting `?-` are queries, everything else is the program.
| `scheme` | BiwaScheme.
| `basic` | The site's own classic BASIC (`static/js/playground-basic.js`); `INPUT` shows a box in the output.
| `rust`, `go` | Sent to play.rust-lang.org / go.dev to compile — add `:network: true` to the page.
| `html` | A sandboxed frame — good for canvas demos.
|===

Every language except HTML, DuckDB, Rust, and Go runs in a Web Worker, so readers can press
*Stop* (or Escape) to end an infinite loop. C, C++, and Python blocks get a *stdin* button. The
runtime is `static/js/playground.js`, loaded by `site.js` only on pages that contain a
playground; the `/tools/sandbox/` page uses the same runtime with a language picker.
Playgrounds work in any kind of page, but collections of them belong in `content/lab/playground/`.

== Voice and structure

* Lead with what the thing is and why it exists; then how; then what you learned.
* For physical builds: materials, tools, the key photos, dimensions that matter, mistakes.
* For software: what it does, how to run it, the interesting design decision, a link to the repo.
* Keep `:summary:` concrete — it is what appears in cards, search, and the feed.

== Tools

A tool is an interactive page under `/tools/`. It has two parts:

. `content/tools/<slug>.adoc` — the title, `:category:` (one of the `tools.categories` ids in
  `site.yaml`: `numbers`, `data`, `encoding`, `crypto`, `time`, `network`), `:summary:`,
  `:tags:`, optional `:network: true` if it contacts other services, and a short "How to use
  it" body (shown collapsed under the tool).
. `static/tools/<slug>.js` — the tool itself, registered with the shared kit:
+
[source,javascript]
----
GW.tool('mytool', (root, k) => {
  const st = k.store('mytool');                 // remembered in localStorage
  const input = k.codeArea({ placeholder: 'Paste here' });
  const out = k.h('pre', { class: 't-out' });
  input.addEventListener('input', () => (out.textContent = input.value.toUpperCase()));
  root.append(k.h('div', { class: 't-panel' }, input, out, k.copyButton(() => out.textContent)));
});
----

The kit (`static/tools/tools.js`) provides element building, tabs, segmented controls, copy
buttons, toasts, file pick/read/download, persistent state, and the `.t-*` styles in
`static/tools/tools.css`. Set `:tool:` if the script name differs from the slug.

[[works-with]]
=== Works with

A tool page can point to the other tools it is genuinely used together with. Name them in the
header, each with one line on why:

[source,asciidoc]
----
:works-with: graph: plot the curve this fit produces; units: convert the inputs first
----

Entries are separated by `;`; in each, the tool's slug (its `content/tools/<slug>.adoc`) comes
before the first `:` and the reason after it, so a reason may contain `:` but not `;`. The reason
is plain text. The page shows a *Works with* panel after the tool and before *How to use it*: each
entry links to `/tools/<slug>/` with that tool's title and category, and the reason. Tools left
out of the build (drafts) are left out of the panel.

Nothing is linked back automatically: if the other tool should point here too, give it its own
`:works-with:` entry, worded from its side. `gw check` reports an entry naming no tool and a
malformed entry (no `:`, no reason, not a slug) as errors — `gw check` then exits with status 1 —
and a tool naming itself or the same tool twice as warnings. `tools_list` and `tool_info` (MCP,
`/api/tools`) include `works_with`.

A site with its own `templates/tool.html` shows the panel by including the built-in partial where
it should appear: `{% include "tool_works_with.html" %}`.

=== Shareable links (deep links)

A tool can make its current configuration shareable as a URL. Call `k.share()` last in the tool's
setup and mark the tool with `:deeplink: true` (the tools index shows a link badge, and a test
checks the two agree):

[source,javascript]
----
k.share({
  state: () => ({ re: pattern.value, flags: flags.value }),        // JSON-serialisable
  apply: s => { pattern.value = s.re ?? ''; flags.value = s.flags ?? ''; update(); },
  readable: ['re', 'flags'],   // short flat state stays human-readable: ?re=a%7Cb&flags=g
});
----

The kit adds a *Share link* button to the tool header and applies state from the URL on load.
State not listed in `readable` (or too long) is packed into `?s=` (deflate + base64url). Readable
parameters arrive as strings, so `apply` coerces numbers and booleans. The selected tab travels in
the `#hash` as before. Keep files, uploads, and secrets out of the state.


==== Tools whose state lives in `k.store`

Most tools already remember their inputs with `k.store`. For those, don't write `state`/`apply`
by hand: await `k.shareStore()` first, before building the UI, and build from the store as usual.
A link then carries the tool's saved settings, and opening one writes them into the store before
the UI exists:

[source,javascript]
----
GW.tool('gears', async (root, k) => {
  await k.shareStore('gears', {
    readable: { m: ['spur.m', 'n'], z1: ['spur.z1', 'n'] },  // ?m=1.5&z1=18 → spur.m, spur.z1
    skip: ['history'],                                       // never shared
  });
  const st = k.store('gears');
  // …build the UI from st as usual…
});
----

`readable` maps short parameters to settings (`'key'`, `'key.field'`, or `[path, 'n' | 'b']` to
coerce hand-written numbers and booleans); an array such as `['data', 'dist']` uses the setting
names themselves. `inbound` adds hand-written parameters that expand into settings
(`{ preset: v => ({ state: PRESETS[v] }) }`), `shared` carries settings kept in another
namespace (`{ ns: 'woodworking', prefix: 'ww:', keys: ['units'] }`), and `scrub` removes
tool-specific secrets before a link is built. `tab`, keys starting with `_`, and values that look
like credentials are never shared. Opening a link replaces the visitor's saved settings, offers
*Restore my settings*, and removes the link from the address bar so a refresh keeps later edits.
